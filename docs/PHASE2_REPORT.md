设计要点：

1. **重连参数位置正确**：`-reconnect*` 与 `-rw_timeout` 放在 `-i` 之前。上游把它们放在 `-i` 之后，实际作用于输出而非输入，属于可疑写法；本项目按 FFmpeg 语义修正。
2. **不做 EOF 重连**：不使用 `-reconnect_at_eof/-reconnect_streamed`，避免直播结束后进程反复拉起、无法收尾。进程异常退出由服务层重新解析处理。
3. **退出码语义**：`0` 视为直播自然结束 → `completed`；非 `0` 才进入续录。避免把下播误判为故障，也避免把故障误判为完成。
4. **有界重试**：退避 2/5/10/20/30 s，最多 5 次；预算耗尽后置 `failed`，原因写明"已尝试 N 次"。不会无限重连。
5. **分段可追溯**：每次续录新建文件与独立历史记录；信号携带 `resumed`、`attempt`，历史可定位每个文件。

## 3. 自动化测试

```
.venv\Scripts\python.exe -m pytest -q
216 passed in 33.47s
```

新增用例覆盖：

- 非零退出 → 分段 1 `failed`（原因含"正在自动续录"）→ 新文件、新记录、`resumed=True`；
- 连续失败 → 达到 2 次预算后停止，最终原因含"已尝试 2 次"，数据库无残留 `recording`；
- 重新解析确认下播 → 不再拉起，会话以 `completed` 结束；
- 等待续录期间手动停止 → 取消重试，不创建空分段；
- 命令参数：HTTP(S) 才启用重连且位于 `-i` 前；本地文件不添加（否则 FFmpeg 报 `Option not found`）。

- 时间：2026-11-18 13:38:27–13:41:53

| 时刻（相对启动） | 事件 |

## 5. 局限与未验证项

以下项目**没有**被本次验证覆盖，不得据代码存在推断为已达标：

1. **弱网真实断开**：只验证了进程被强杀；TCP 半开/丢包场景下 `-reconnect 1` 是否阻止进程退出，需弱网工具验证。
2. **流地址真实过期**：续录前确实重新解析，但未构造"旧地址过期 + 新地址可用"的完整时序。
3. **真实下播事件**：`status=4` 分支仅用桩验证；未等待真实主播下播。
4. **长时间稳定性**：未覆盖 >1 h 连续录制与跨天。
5. **多房间并发**：未做 10+ 房间压测；已知限制是续录解析在录制管理线程中同步执行，极端情况下会延迟其他房间的轮询（≤解析超时）。
6. **续录分段完整性**：未对续录产生的第二个文件做 MPEG-TS 逐包连续性分析（临时目录已随测试清理）。
7. **开播发现时延**：默认轮询间隔 120 s 未改动，未测真实开播事件。

## 6. 仍存在的结构性差距（不属本轮范围）

| 差距 | 影响 | 建议 |
| --- | --- | --- |
| 解析单数据源、无签名 | 页面改版/风控时可能整体失效 | 单独立项评估第二数据源与纯 Python 签名 |
| 解析 2.9× 慢、1.34 MB/次 | 单房间约 0.96 GB/日，开播发现延迟被放大 | 评估轻量接口或条件请求（ETag/Last-Modified） |
| 无清晰度探测/换档 | 拿到不可用地址时无备选 | 需真实多档样本后实现 |
| 启动不自动恢复监控 | 重启后值守中断 | **需产品确认**是否改为"启动即恢复监控" |
| 短链/主页链接不支持 | 输入体验差距 | 低优先级 |
