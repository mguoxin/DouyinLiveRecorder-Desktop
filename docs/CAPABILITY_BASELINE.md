## 2. 方法

### 2.1 解析（`parse_bench.py`）

- 两侧各 **N=30** 次串行请求，间隔 3 s，同一房间、同一时段先后执行。
- 计时范围：从发起请求到解析结果产生（含网络、解析；本项目不含磁盘）。
- 成功判定：本项目 `ParseResult.SUCCESS` 且能取到 `status`；上游 `status ∈ {2,4}` 且 `anchor_name` 非空。
- 本项目额外记录每次响应体字节数（用于评估轮询开销）。

### 2.2 连续录制（`rec_bench.py`）

- 两侧各录制 **600 s**，串行执行，使用各自**实际生产命令**：
  - 本项目：[ffmpeg.py:104 `build_record_command`](file:///c:/Users/kglpl/Desktop/DouyinLiveRecorder-Desktop/src/dlrecorder/infrastructure/ffmpeg.py#L104-L127) 的 8 参数命令（`-c copy -f mpegts`）。
  - 上游：`main.py` 中抖音 FLV+TS 分支的完整参数（`-rw_timeout`、`-reconnect_streamed`、`-reconnect_at_eof`、`-reconnect_delay_max 60`、`-max_muxing_queue_size` 等）。
- 采样：每 1 s 记录输出文件大小；每 1 s 读取 FFmpeg 进程 CPU 时间（`GetProcessTimes`）与工作集（`GetProcessMemoryInfo`）。
- 结束：向 stdin 写入 `q`，10 s 内退出记为优雅收尾。
- 流地址：分别取两套实现自己解析出的地址——本项目 `FULL_HD1`（`uhd`），上游默认"原画"（`or4`）。**清晰度不同，字节数与 CPU 不可直接横比；结构性指标（丢包、断层、起录时延）可比。**

### 2.3 文件完整性（`ts_analyze.py`）

不依赖 ffprobe（项目内置 FFmpeg 不含 ffprobe），直接解析 MPEG-TS 188 字节包：

- 每个 PID 的 continuity_counter 跳变次数 → 传输层丢包；
- PCR（program clock reference）时间跳变 → 媒体时间断层（丢片）。

## 3. 结果：解析

| 指标 | 本项目 0.1.1 | 上游 add187f8 |
| --- | --- | --- |
| 成功率 | **30/30 (100%)** | **30/30 (100%)** |
| 时延 最小 / 中位 / P95 / 最大 | 1124 / **1478** / 2461 / 2525 ms | 422 / **504** / 611 / 757 ms |
| 返回 status | 2（直播中） | 2（直播中） |
| 单次响应体 | ≈ **1.34 MB**（整页 React Flight） | JSON 接口（本次未计字节） |
| 数据源 | 公开直播页内嵌数据（单一来源） | `web/enter` 接口（带 `a_bogus`），另有 app 接口与页面两层回退 |

结论：

1. 在**当前页面结构下**两者都能稳定解析，成功率无差异。
2. 本项目单次解析时延约为上游 **2.9 倍**（1478 ms vs 504 ms），P95 约为 **4 倍**。原因是每次轮询都会下载约 1.34 MB 的完整页面并做字符串拼接 + JSON 还原，而上游请求的是小体积 JSON。
3. 按本项目默认监控间隔 120 s（[settings_service.py:25](file:///c:/Users/kglpl/Desktop/DouyinLiveRecorder-Desktop/src/dlrecorder/application/settings_service.py#L25)）计算，**单房间每日轮询流量约 0.96 GB**（720 次 × 1.34 MB），且延迟会直接体现在开播发现时延上。
4. 上游具备三层数据源回退与签名能力，本项目只有单一页面数据源；本次未遇到风控/改版，因此**"抗改版能力"未被验证**，只记录为结构性差异。

## 5. 结果：故障恢复（录制中强杀 FFmpeg）

- 场景：直播进行中，用 `taskkill /F` 杀掉 FFmpeg 子进程，模拟"录制进程异常退出"，观察 150–180 s。
- 本项目：通过 `RecordingService` 真实驱动（临时 DB、临时输出目录、`poll_interval_s=0.2`），杀进程后持续 `processEvents` 并采样文件大小与 FFmpeg 进程数。
- 上游：运行其 `main.py`（临时目录、临时配置），待文件出现并增长 60 s 后杀掉 FFmpeg，观察是否自动重新拉起。

### 5.1 本项目 0.1.1

| 项目 | 实测值 |
| --- | --- |
| 杀进程时刻 | t = 60.6 s |
| 杀进程时文件大小 | ≈ 48 MB |
| 状态变化 | t = 62.4 s（+1.8 s）→ `failed`，原因 `FFmpeg 退出码 1` |
| 会话是否结束 | 是（`remaining_active=0`，线程正常退出） |
| 观察窗（150 s）采样 | 99 次，文件大小恒为 **48.0 MB**，FFmpeg 进程数恒为 **0** |
| 是否自动续录 | **否** |
| 恢复时延 | **未恢复（≥150 s 内 0 次拉起）** |
| 录制缺口 | 从 t=60.6 s 起持续到会话结束；直播仍在进行，但录制已永久停止 |

### 5.2 上游 add187f8

| 项目 | 实测值 |
| --- | --- |
| 启动到出文件 | 6.0 s |
| 杀进程时刻 | t = 66.0 s（文件 76.8 MB） |
| 新文件出现 | t = 93.6 s → **杀后 27.6 s 自动续录** |
| 产出文件 | 2 个：62.5 s / 77.6 MB；157.3 s / 187.2 MB |
| 两个文件完整性 | continuity_counter 丢包 0，PCR 断层 0 |
| 行为 | FFmpeg 退出 → 外层循环重新解析并新建文件，录制继续 |

### 5.3 结论

这是本次基线中**唯一的定性差距**，且属于功能性缺失而非参数调优问题：

- 上游把"FFmpeg 退出"当作可恢复事件，**27.6 s 内**重新拉流并续录，代价是一个 23–28 s 的媒体缺口和一个新文件；
- 本项目把"FFmpeg 退出"当作会话失败，状态置为 `failed` 后不再尝试，**直播继续但录制终止**；
- 本项目当前命令也没有任何 `-reconnect_*` 参数，因此网络抖动导致 FFmpeg 退出时，表现与强杀相同。

## 7. 结构性差距（基于代码 + 本次实测）

1. **单一解析数据源**：本项目只读公开页；上游三层回退。本次未触发风控，因此差距体现为**风险**而非**当前失败**。
2. **无流地址刷新**：录制启动后不再解析；上游在 FFmpeg 退出后由外层循环重新获取地址并续录。
3. **FFmpeg 无重连参数**：本项目命令不含任何 reconnect 选项，连接中断即退出；上游含 `-reconnect_streamed/-reconnect_at_eof/-reconnect_delay_max 60`。
4. **轮询成本**：1.34 MB/次、默认 120 s 间隔，单房间约 0.96 GB/日；上游为小 JSON。
5. **无地址可用性探测与清晰度选择**：本项目取固定键序第一个地址；上游会探测并自动换档。

## 8. 局限与结论边界

- 只测了 **1 个直播间、1 条网络、1 个时段**，样本量不足以给出统计意义上的可靠性结论。
- 两套实现选流档位不同，字节数、CPU 不能直接横比。
- 上游为对齐口径修改了 5 项配置（分段/转码/推送/代理/循环时间），这些功能本身未纳入测量。
- 未测量开播发现时延：需要房间从"未开播"变为"直播中"的真实事件，本次房间已在播。
- 未测量流地址过期与长时间运行：需跨越数小时。
- 上游的 27.6 s 续录时延受其 `循环时间(秒)` 配置影响：本次为缩短实验设为 **30 s**（仓库默认 300 s），因此该数值代表"重新拉流+起录"的能力下界，不代表默认配置下的开播/续录时延。本项目侧的 150 s 观察窗同样远长于其 `poll_interval_s=0.2` 的检测周期，未恢复不是观察时间不足造成的。
- 本报告**不构成**"本项目核心能力已达上游水平"的结论；它只说明：在**稳定网络 + 单房间 + 10 分钟**这一窄条件下，两者的录制质量相同，而解析效率与故障恢复能力存在明确差距。
