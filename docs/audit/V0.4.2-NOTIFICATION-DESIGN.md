# V0.4.2 录制失败通知设计（B-04）

- 目标：低打扰、语义准确、可去重、可降级，且不改变录制行为
- 约束：不弹模态框、不阻塞录制线程、不引入新依赖、不改数据库 Schema
- 依据：`V0.4.2-RELIABILITY-AUDIT.md` 中 RA-02/RA-03/RA-04

## 1. 设计原则

1. **一次可自动恢复的中断不是“永久失败”**：必须显示“重连中（第 x/5 次，N 秒后）”，
   不得使用“录制失败”字样。
2. **只有重试预算耗尽或不可重试错误才发失败通知**。
3. **恢复后只提示一次“已恢复”**，避免每次分段成功都打扰。
4. **同一直播间同一类错误 60 秒内只提醒一次**；状态栏仍每次更新。
5. **多房间同时异常合并提醒**，避免通知风暴。
6. **通知失败不影响录制**：通知组件任何异常都被捕获并降级为日志。
7. **托盘不可用时降级**到状态栏 + 房间行徽标 + 日志页，不弹模态框。

## 2. 事件模型改造

### 2.1 现状问题

- `recording_error(room_id, message)` 不足以区分“启动失败 / 运行失败 / 数据库失败”，
  也无法表达“是否会自动恢复”（RA-02）。
- 分段失败只发 `recording_finished(scope=segment,status=failed)`（RA-03）。
- `recording_reconnecting` 已带 `attempt/max_attempts/delay_s/error`，信息足够。
- `recording_started` 已带 `resumed` 与 `attempt`，可表达恢复。

### 2.2 建议载荷（增量、非破坏性语义）

将 `recording_error` 的第二参数从 `str` 扩展为 `dict`（内部信号，消费端仅
`main_window.py` 与 5 处测试；一并更新）：

```python
{
  "phase": "start_failed" | "runtime_failed" | "session_failed" | "db_failed",
  "category": "disk" | "output_dir" | "network" | "auth" | "process" | "database" | "other",
  "retryable": bool,
  "message": str,          # 已脱敏，保留原文供状态栏/日志
}
```

- 分类在 `RecordingService` 产生错误的位置直接给出，禁止 UI 用文本正则反推。
- `recording_finished` 已含 `scope/status/error/file_size`，不再扩展；
  通知层按 `scope == "session" and status == "failed"` 触发失败通知，
  按 `scope == "segment" and status == "failed"` 触发“本段失败、将继续监控”的弱提示。
- 新增 `recording_recovered = Signal(int, dict)`：在续录成功建立新分段后发出
  `{attempt, file_path}`；与 `recording_started(resumed=True)` 二选一即可，
  建议显式信号，避免 UI 依赖 `resumed` 推断。

### 2.3 事件到用户语义映射

| 内部事件 | 用户看到 | 通知级别 |
| --- | --- | --- |
| `recording_started(resumed=False)` | “开始录制” | 无气泡 |
| `recording_reconnecting` | 房间行“重连中 2/5，12 秒后”；状态栏同步 | 无气泡（首次进入重连可状态栏提示） |
| `recording_recovered` | “已恢复录制（第 2 次重连成功）” | 信息气泡，每场最多 1 次 |
| `recording_finished(segment, failed)` | “本段录制中断，仍在监控” | 信息/警告气泡，按去重 |
| `recording_finished(session, failed)` + `recording_error(session_failed)` | “录制结束：已达重试上限/无法开始” | 警告气泡，按去重 |
| `recording_error(start_failed, retryable=False)` | “无法开始录制：磁盘空间不足” | 警告气泡，按去重 |
| `recording_error(start_failed, retryable=True)` | “暂时无法开始，稍后重试” | 状态栏 + 房间行 |

## 3. 组件设计

新增 `src/dlrecorder/presentation/notification_center.py`（纯 UI 层，QObject）：

```
NotificationCenter(QObject)
  __init__(tray, status_bar, room_list, clock=time.monotonic)
  on_started(room_id, snapshot)
  on_reconnecting(room_id, snapshot)
  on_recovered(room_id, snapshot)
  on_finished(room_id, snapshot)
  on_error(room_id, payload)
  tick()  # 可选：合并窗口到期后统一发出
```

职责：

- 维护 `room_id → RoomNoticeState`（`idle / retrying / failed`）与最近错误类别。
- 去重表 `(room_id, category) → last_emitted_monotonic`，窗口 60 秒。
- 恢复通知每场会话最多 1 次（以 `recording_started` 首次重置）。
- 通知风暴合并：3 秒内待发通知 ≥ 3 条时，合并为
  “3 个直播间录制异常，点击查看日志”，只发一条。
- 所有入口 `try/except` 包裹，异常写 `logger.exception`，绝不向上抛。
- 不访问数据库以外的网络；不读取 Cookie；不阻塞（无 sleep、无 join）。

托盘扩展（`tray.py`）：

- `show_message(title, message, severity="info"|"warning")`，内部映射
  `QSystemTrayIcon.MessageIcon.Information/Warning`；保留 4 秒超时。
- 托盘不可用（`_tray is None`）时，`NotificationCenter` 自动只走状态栏 + 房间行 + 日志。

房间行（`widgets.py:RoomListWidget`）：

- 录制列新增状态值：`录制中` / `重连中（2/5）` / `录制失败`。
- 失败后保留红色徽标，用户点击/开始新录制时清除；不改变列数与布局骨架。

状态栏（`main_window.py`）：

- 保留单行文本；通知中心负责措辞，状态栏不再由多个信号互相覆盖（按时间戳最后写入，
  但重连→恢复有明确顺序）。

## 4. 去重与风暴控制算法

```
key = (room_id, category)
if key in last_emit and now - last_emit[key] < 60s: return
last_emit[key] = now
pending.append(notice)

# flush 时（同一事件循环批次 / 3 秒窗口）
if len(pending) >= 3:
    emit_one(f"{len(pending)} 个直播间录制异常，可在“日志”页查看详情")
else:
    for n in pending: emit_one(n)
```

- 不同类别（如 network 与 disk）分别计时，互不吞并。
- 同一房间 60 秒内从“网络中断”升级为“最终失败”时，允许立即发送失败通知（更高严重度），
  并重置该 key 的计时。
- 恢复通知不受 60 秒去重限制，但受“每场一次”限制。

## 5. 文案规范（示例）

| 场景 | 标题 | 正文 |
| --- | --- | --- |
| 启动失败-磁盘 | 无法开始录制 | 「房间名」磁盘剩余空间不足，请清理后重试 |
| 运行中断-重连 | 正在自动续录 | 「房间名」连接中断，12 秒后第 2/5 次尝试 |
| 恢复 | 已恢复录制 | 「房间名」第 2 次重连成功，已写入新分段 |
| 分段失败 | 本段录制中断 | 「房间名」本段已保存，监控继续 |
| 最终失败 | 录制已停止 | 「房间名」连续 5 次续录失败，请检查网络或稍后重试 |
| 多房间异常 | 多个直播间录制异常 | 3 个直播间受影响，详情见日志页 |

禁止出现：`status=completed size=0` 之类内部字段、完整流地址、签名参数、Cookie。

## 6. 测试计划

单元（新增 `tests/test_notification_center.py`，使用可注入时钟）：

1. 60 秒内同房间同类错误只发 1 条；61 秒后再次发送。
2. 不同房间/不同类别互不抑制。
3. 重连事件不产生失败气泡，只更新房间行。
4. 恢复事件每场最多 1 条。
5. 3 秒内 3 个房间异常合并为 1 条汇总。
6. 托盘为 None 时不调用 tray，仍更新状态栏与房间行。
7. 通知组件内部抛异常时录制事件处理不受影响（注入故障）。
8. 分段失败触发弱提示；会话失败触发警告提示。

集成（offscreen，扩展 `test_app.py`）：

- 模拟 recording_error(dict) → 检查状态栏文本、房间行状态、tray 调用计数。
- 模拟重连→恢复序列，检查“重连中”状态被清除。
- 关闭期间到达通知不崩溃（窗口已禁用/隐藏）。

## 7. 修改文件、风险与回滚

| 文件 | 改动 |
| --- | --- |
| `application/recording_service.py` | `recording_error` 载荷改 dict；新增 `recording_recovered`；错误产生点补 category/retryable |
| `presentation/notification_center.py` | 新增（约 150–200 行） |
| `presentation/tray.py` | `show_message` 增加 severity 参数 |
| `presentation/widgets.py` | 房间行“重连中/失败”状态；不改布局骨架 |
| `presentation/main_window.py` | 接入通知中心，移除重复的状态栏竞争逻辑 |
| `tests/test_recording_service.py` 等 | 5 处 `recording_error` 断言改 dict |

风险：

- R1 事件载荷变更导致旧测试失败 → 一次性更新测试，CI 必须全绿。
- R2 通知在 GUI 线程高频触发 → 所有入口只做内存操作；合并窗口防止风暴。
- R3 文案过长撑破托盘 → 正文截断 120 字符。
- R4 恢复通知误报（重连后又失败）→ 只在 `recording_recovered` 时发，且每场一次。

回滚：通知中心为独立模块，若线上异常，`MainWindow` 恢复原状态栏处理并停止连接新信号；
服务层 dict 载荷可保留（向后兼容消费者需同步回退）。改动不涉及数据库与发布资产，回滚成本低。

## 8. 验收标准

- 断网 1 次（模拟）→ 只看到“重连中”，无“失败”字样；恢复后 1 条“已恢复”。
- 连续 6 次失败 → 只收到 1 条最终失败通知（60 秒内），状态栏每次更新。
- 5 个房间同时失败 → 1 条汇总通知，无通知风暴。
- 托盘不可用 → 功能正常，无崩溃，信息可见。
- 通知组件故障注入 → 录制状态机与文件输出不受影响。
- 全部现有 284 项测试 + 新增测试通过；CI 绿。
