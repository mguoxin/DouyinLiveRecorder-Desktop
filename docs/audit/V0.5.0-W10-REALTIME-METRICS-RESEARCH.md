## 2. 现状数据来源盘点

### 2.1 已有能力（可直接复用）

| 数据 | 现有来源 | 代码位置 | 频率 | 说明 |
| --- | --- | --- | --- | --- |
| 输出文件字节数 | `file_size(Path)` → `stat().st_size` | `infrastructure/ffmpeg.py` `file_size()`；`recording_service.py` L612 | 1 秒 | 已在停滞检测中使用，属于最可靠的数据源 |
| 最近增长时刻 | `_ActiveRecording.last_growth_at` | `recording_service.py` L86、L613-L615 | 1 秒 | `time.monotonic()`，不受系统时钟调整影响 |
| 上次采样大小 | `_ActiveRecording.last_size` | L85、L614 | 1 秒 | 可自然扩展为速度差分基线 |
| FFmpeg 存活/退出码 | `FFmpegProcess.poll()` | `ffmpeg.py` L396 | 1 秒 | 不阻塞 |
| 进程 PID | `FFmpegProcess.pid` | `ffmpeg.py` L337-L339 | — | 可用于进程 I/O 计数（实验性） |
| stderr 尾部 | `stderr_tail()` + 专用排空线程 | `ffmpeg.py` L372-L394 | 实时 | 已脱敏；当前用于错误诊断 |
| 分段开始/结束时间 | `recordings.started_at / ended_at` | `db.py` L205-L219 | 事件驱动 | UTC ISO 字符串，可推导历史时长 |
| 分段最终大小 | `recordings.file_size` | `db.py` L212；`_close_segment` L993 | 事件驱动 | 仅分段结束写入 |
| 房间状态（录制/重连/失败） | `recording_*` 结构化信号 | `main_window.py` L226-L232、L536-L617 | 事件驱动 | UI 已有状态胶囊 |

### 2.2 关键缺口

1. **没有分段开始时刻的内存记录**：`_ActiveRecording` 只有 `last_size / last_growth_at`，没有 `segment_started_at`。历史时长可读数据库，但"正在录制多久"无法直接得出（可读 `recordings.started_at` 再做时区解析，但会额外查库且粒度只到秒，不如内存单调时钟直接）。
2. **没有速度差分**：目前只比较"是否增长"，不计算增长速率，也不保留历史采样。
3. **stdout 被丢弃**：录制命令以 `stdout=DEVNULL` 启动（`ffmpeg.py` L355），FFmpeg 的 `-progress` 输出当前不可用。
4. **stderr 仅保留尾部 40 行**（`DEFAULT_STDERR_TAIL_LINES`），没有结构化解析；`-loglevel warning` 下本身也不输出统计行。
5. **数据库不可扩展**：Schema v2 冻结，`recordings` 表不能新增 `duration/bitrate` 列。任何指标持久化都必须走"不写库"或"另建表"（本轮不建议）。
6. **界面没有指标承载位**：房间表固定 7 列（`COLUMNS`，`widgets.py` L68；测试 `tests/test_app.py` L427 断言 `columnCount() == 7`），没有详情面板。

### 2.3 结论

> 现有 1 秒轮询已经提供了"文件大小时间序列"的骨架，**文件写入速度、当前文件大小、分段时长、停滞时长、健康状态**可以在不新增线程、不新增依赖、不改命令的前提下实现。
>
> **媒体比特率、FFmpeg 速度比**无法从文件大小可靠推导，必须依赖 FFmpeg `-progress`；**网络下载速度**在本架构中没有低成本精确来源，只能做估算或不展示。

## 3. 指标定义与语义区分（核心）

### 3.1 四种"速度"必须分开

| 指标 | 严格定义 | 本项目数据源 | 可靠度 | 是否建议展示 |
| --- | --- | --- | --- | --- |
| **文件写入速度** | 输出文件字节数增长率：`Δsize / Δt` | `stat()` 差分 | 高（受 OS 写缓存影响，呈突发性） | **是**，主指标，界面标注“写入速度（估算）” |
| **网络下载速度** | FFmpeg 从输入 URL 实际读取的字节速率 | 无直接来源；`GetProcessIoCounters` 仅作实验 | 低（socket 读取可能不计入 I/O 计数器） | **本期不展示，也不投入专项验证**（决策 7） |
| **媒体比特率** | 媒体流本身的编码码率：`输出字节×8 / 媒体时长` | FFmpeg `-progress` 的 `bitrate` / `total_size` + `out_time_us` | 高（FFmpeg 计算） | **是**，二期展示 |
| **FFmpeg 速度比** | `已处理媒体时长 / 实际耗时`，即 `speed=` | FFmpeg `-progress` 的 `speed` | 高 | **是**，二期展示 |

**禁止的替代关系**（必须在实现与文案中避免）：

- 不得把"文件写入速度 × 8"标为"码率"：MPEG-TS 封装开销（188 字节包、PAT/PMT、空包填充）会使两者相差数个百分点；断流时写入速度下降但媒体码率不变。
- 不得把"文件写入速度"标为"下载速度"：磁盘写缓存会让文件大小滞后于网络接收；FFmpeg 的 muxer 队列（`-max_muxing_queue_size 1024`）也会吸收突发。
- 不得把 `speed=1.0x` 理解为"网络速度"：`-c copy` 下它接近 1.0 只表示音视频时间轴与墙钟同步；`speed<1` 才提示处理落后（通常伴随缓冲/写入瓶颈）。

### 3.2 其余指标定义

| 指标 | 定义 | 数据源 | 备注 |
| --- | --- | --- | --- |
| 当前文件大小 | 当前分段输出文件字节数 | `stat()` | 断流时数值冻结，不置零 |
| 本场累计大小 | 会话内已完成分段 + 当前分段 | 内存累加 + `stat()` | 分段切换时累加，不查库 |
| 分段录制时长 | 当前分段已录制墙钟时长 | 新增内存 `segment_started_at`（单调时钟） | 一期即可 |
| 媒体时长 | FFmpeg 已处理媒体时间 | `-progress` `out_time_us` | 二期；与墙钟的差值可反映落后 |
| 本场有效录制时长 | 各分段时长之和（不含重连等待） | 内存累加 | 与"会话时长"分开，避免把重连等待算作录制 |
| 停滞时长 | 距最近一次文件增长的秒数 | `now - last_growth_at` | 已有字段，直接展示 |
| 健康状态 | 由多个信号推导的枚举 | 见 §3.3 | 不与 W-01/W-02 的房间状态重复 |

### 3.3 健康状态机（建议）

优先级从高到低，命中即停止：

| 状态 | 判定条件 | 展示 |
| --- | --- | --- |
| 失败 | 已有 `failed` 房间状态 / 进程退出且无法续录 | 红（`danger`） |
| 重连中 | `process is None` 且存在重试计划 | 黄（`warning`），显示第 x/y 次 |
| 停滞 | 无增长 ≥ 30 秒（`STALL_WARN_S`） | 红（`danger`），显示"已 N 秒无数据" |
| 降速 | 最近 30 秒写入速度 < 前 60 秒均值的 40% | 黄（`warning`） |
| 恢复中 | 新分段启动后 10 秒内（`RECOVER_GRACE_S`） | 中性（`text_muted`），避免启动瞬间误报 |
| 良好 | 10 秒内有增长，且不在上述状态 | 绿（`success`） |

阈值全部设为模块常量，不进入设置页（决策 4）。当前数值为**待校准初值**：一期开发前须用合成增长曲线与真实 FFmpeg 短录制样本校准，并在测试报告中记录误报率；校准结果可以调整常量，但不得新增用户配置项。

> 说明：健康状态是**展示层的派生值**，不写入数据库，不改变录制状态机，也不触发已有 `stall_timeout_s=120s` 的自动续录逻辑。**"数据停滞"只表示健康状态降级，不等于"录制失败"**；是否失败仍由现有进程退出、续录预算与分段结果决定。

## 4. 采样方案

### 4.1 方案 A（一期唯一采集方案，已批准）

**复用现有 1 秒轮询，不新增线程、不新增依赖、不改 FFmpeg 命令、不改数据库字段。**

```
recording_service._poll_active()
  └─ 每 tick，对每个 process 非空的 active：
       1. size = file_size(path)                    # 已有
       2. delta = size - last_size                  # 新增
       3. 记录 (monotonic_now, size) 到环形缓冲      # 新增
       4. 若 delta > 0：更新 last_growth_at          # 已有
       5. 计算 5 秒滑动窗口写入速度 = Σ(最近 5s delta)/5
       6. 更新只读快照（受 _active_lock 保护）
```

- 环形缓冲：`deque(maxlen=120)`，1 秒一点 = 120 秒趋势；每房间约 2 KB 内存。
- 平滑：展示用 **5 秒滑动窗口**，抑制 Windows 写缓存导致的"1 秒 0、下一秒 4 MB"抖动；趋势图直接用 1 秒点。
- 读取接口：`RecordingService.metrics_snapshot(room_id)` 返回普通 `dict` 拷贝，UI 线程调用；内部加锁时间 O(1)。
- 不新增逐房间信号：避免 20 房间 × 1 Hz 的信号风暴；UI 用 `QTimer(1000)` 主动拉取。

**可覆盖指标**：文件大小、分段/本场时长、估算写入速度、停滞时长、健康状态（含降速判定）、写入速度趋势图。
**不可覆盖**：媒体比特率、FFmpeg 速度比、网络下载速度。

### 4.2 方案 B（二期候选，本期不实施、不批准改命令）

在 `build_record_command` 增加：

```
-progress pipe:2 -nostats -stats_period 1
```

选择 `pipe:2`（stderr）而非 `pipe:1` 的原因：

- 现有 stderr 已有专用排空线程（`_drain_stderr`），不需要为每个进程新增 stdout 读线程；
- stdout 保持 `DEVNULL`，不改变既有进程模型；
- `-nostats` 关闭默认统计行，避免与 `-progress` 重复。

解析要点：

- `_drain_stderr` 中识别 `out_time_us=`、`total_size=`、`bitrate=`、`speed=`、`drop_frames=`、`progress=continue|end`；
- **识别为进度行的内容不进入 `_stderr_tail`、不写入诊断日志**，否则 40 行尾部会被进度块挤占，错误诊断能力下降；
- 仅在 `progress=continue`（块结束）时提交一次解析结果，避免半块数据；
- 解析失败静默降级为方案 A，不得影响录制。

**码率语义核实要求（决策 8）**：`-progress` 的 `bitrate` 由 FFmpeg 依据**输出侧** `total_size / out_time` 计算，属于输出封装统计，包含 MPEG-TS 封装开销，**不等同于原始视频编码码率**。二期立项前必须用同一录制文件做对照：`ffprobe` 读取输出文件的 `bit_rate` 与 `-progress` 值比对，并记录差异范围；若无法证明其语义满足展示需求，则二期只展示"输出码率（估算）"或直接放弃该指标。**本期不修改命令，不做该项验证的代码改动。**

风险：

- 改动录制命令属于"已验证稳定核心"边界，需专项回归（含真实 FFmpeg 冒烟）；
- `speed`/`bitrate` 字段在极短分段或异常退出时可能缺失，需容错；
- Windows 上 stderr 混入进度块，若过滤不严会污染错误日志 → 必须先用"字段白名单"解析，未知行原样进入尾部日志。

### 4.3 方案 C（不推荐）

- 解析 `-stats` 的 stderr 汇总行：`-loglevel warning` 下默认关闭，且格式随版本变化大；
- 额外调用 `ffprobe` 轮询：进程开销与磁盘 I/O 明显高于收益；
- 第三方带宽/磁盘监控库：引入新依赖，违背项目约束。

### 4.4 采样开销与限制

| 项 | 估算 | 说明 |
| --- | --- | --- |
| `stat()` 单次 | 约 0.02–0.2 ms | 本地 NTFS；杀毒软件实时扫描、网络盘、机械盘可能更高 |
| 20 房间每 tick | 约 0.4–4 ms | 串行执行；1 秒一次，占比可忽略 |
| 环形缓冲写入 | O(1) | `deque.append` |
| UI 拉取 | O(房间数) | 仅取选中房间或可见行，实际更小 |

> 上述为**预算估算，未实测（NOT TESTED）**。若目标环境包含网络盘或强杀毒环境，需在 v0.5.0 验收阶段实测单 tick 耗时并设置上限（建议 < 20 ms / 50 房间）。

## 5. 统计规则与边界情况

| 场景 | 规则 |
| --- | --- |
| **多房间并发** | 每房间独立基线、独立环形缓冲；互不共享窗口；总写入速度仅在 UI 汇总时求和，不额外采样 |
| **分段切换（自动续录）** | 新分段：`last_size=0`、`segment_started_at=now`、清空环形缓冲；`session_bytes += 上一分段最终大小`；禁止用新分段 0 字节与旧分段大字节做差分（会产生负值/巨大跳变） |
| **等待重连（`process is None`）** | 冻结指标，不向趋势图补 0；健康状态显示"重连中"；`有效录制时长` 不计入等待时间 |
| **重连成功** | 进入 10 秒恢复宽限期；首次观察到文件增长后才发 `recording_recovered`（现有语义 L616-L626，保持不变）；宽限期内健康状态为"恢复中" |
| **手动停止** | UI 停止拉取；保留最终快照至房间行变为 idle；`有效录制时长` 截止到停止时刻 |
| **直播自然结束（退出码 0）** | 与手动停止一致；不把"结束"误判为"停滞"（进程已退出，健康状态走 `failed/completed` 分支） |
| **文件缓冲 / 写缓存** | 只接受单调递增的大小；`delta<0` 视为异常重置基线并记 debug 日志（正常不应出现）；展示速度用 5 秒窗口平滑 |
| **磁盘写入延迟** | 若文件大小 30 秒无增长但 FFmpeg 仍存活 → 先标"停滞"，120 秒后由现有逻辑重启（不新增重启路径）。是否区分"网络停滞 vs 磁盘停滞"依赖进程 I/O 计数，列为实验项 |
| **磁盘空间不足** | 现有逻辑直接停止录制并报错；指标面板同步显示"已停止（磁盘不足）"，不再显示速度 |
| **进程无法确认退出** | 现有逻辑不续录；指标面板显示最后已知大小，不显示速度 |
| **系统休眠/时钟跳变** | 全程使用 `time.monotonic()`；休眠唤醒后首个 tick 的 `Δt` 过大时重置窗口，避免速度被摊薄 |
| **窗口隐藏/最小化/托盘** | UI 定时器暂停拉取（`isVisible()`/`isMinimized()` 判断），采样照常（已由录制轮询完成） |

## 6. UI 集成方案

### 6.1 约束

- 房间表固定 7 列，测试断言 `columnCount() == 7`；`录制` 列宽 116，已容纳"重连中 x/y"，**不建议再加列**。
- 视觉必须复用 `theme.py` 语义令牌（`surface / surface_alt / border / text_muted / accent / accent_soft / success / warning / danger` 及其 `_soft`），不得写死颜色。
- 交互风格与现有卡片、状态胶囊、只读表格一致；无动画、无第三方图表库。

### 6.2 推荐方案：房间页底部"录制详情"面板

在 `RoomsPage` 的表格卡片下方增加一条可折叠面板（高度约 64–72 px），仅显示**当前选中房间**的指标。交互规则（决策 3）：

- **无选中房间时面板完全隐藏**，不保留空白占位，表格恢复原有高度；
- 首次选中房间时**默认展开**；
- 用户可以手动收起/展开；手动收起后，同一次运行内切换房间保持收起状态（尊重用户选择）；
- 清空选中后重置为"下次选中时默认展开"；
- 面板状态不写入设置、不持久化，避免引入配置项。

```
┌───────────────────────────────────────────────────────────────────────┐
│ ● 录制中   已录制 00:42:18   文件 1.28 GB   写入 1.6 MB/s   健康 良好  │
│ 本场累计 3 个分段 · 2.05 GB            ╱╲    ╱╲╱   (120×32 趋势线)     │
└───────────────────────────────────────────────────────────────────────┘
```

- 选中但未录制：显示 `text_muted` 文案"该直播间当前未录制"。
- 重连中：状态点变黄，写入显示 `—`，附"第 x/y 次自动续录"；不显示 0 B/s。
- 停滞：状态点变红，写入 `0 B/s`，文案"已 N 秒无数据"。
- 二期在"写入"后追加"码率 2.4 Mbps · 速度 1.00x"；一期不显示这两个字段，避免用错误数据填充。

### 6.3 趋势图（一期最小版，已批准）

- 自绘 `QPainter` 迷你折线（`QWidget` 子类，约 120×32），数据来自环形缓冲最后 120 点（2 分钟）。
- 线条用 `tokens.accent`；停滞区间用 `tokens.warning` 覆盖背景带；无渐变动画。
- 仅面板可见时重绘（1 Hz），隐藏时停止；窗口最小化、进入托盘、切换到其他页面时同样停止（决策 6）。
- 仅更新当前选中房间，不遍历整表；数值未变化时跳过重绘；无动画、无渐变动效。

### 6.4 辅助入口

- **状态栏**：暂不纳入一期（决策 2 未包含），保留为后续候选。
- **Tooltip**：录制列 tooltip 追加"已录制 … · 写入 … · 健康 …"，无需改列宽。
- **设置页**：**一期不加开关**（采样开销可忽略，始终开启）。若二期启用 `-progress`，再评估增加"显示实时指标（每秒刷新）"开关，默认开启。

### 6.5 文案与单位

| 指标 | 格式 | 示例 |
| --- | --- | --- |
| 文件大小 | 复用 `_format_size` 规则（B/KB/MB/GB，1 位小数） | `1.3 GB` |
| 写入速度 | KB/s 或 MB/s，1 位小数 | `1.6 MB/s` |
| 码率 | Mbps，2 位小数 | `2.40 Mbps` |
| 速度比 | `x`，2 位小数 | `1.00x` |

需在 tooltip/帮助中说明"写入速度受磁盘缓存影响，短时波动属正常"，避免用户把抖动当故障。

## 7. 性能预算

| 项 | 预算 | 备注 |
| --- | --- | --- |
| 采样 CPU（20 房间） | < 0.5%（1 核占比） | 仅 stat + 差分；**未实测** |
| 采样 CPU（50 房间） | < 1.5%，单 tick < 20 ms | 网络盘/杀毒环境需单独验收 |
| 内存 | 约 2 KB/房间（120 点）+ 快照字典 | 20 房间 < 60 KB |
| UI 重绘 | 1 Hz，单面板约 1–2 ms | 仅可见时；隐藏/最小化暂停 |
| 磁盘 I/O | 每秒 1 次 stat/房间 | 不读取文件内容，不扫描目录 |
| FFmpeg 影响 | 方案 A 为 0；方案 B 每秒约 1 个进度块（< 300 B） | 远低于现有 stderr 日志量 |

**验收阈值（决策 10，强制实测）**：在目标机与一台低配设备上，以 50 个活动录制房间运行性能用例：

- 管理线程单 tick 增量耗时：均值 < 10 ms，p95 < 20 ms；
- GUI 进程 CPU 增量 < 1%（1 核占比），RSS 增量 < 20 MB；
- Qt 主线程无新增阻塞调用；
- 必须记录设备规格、系统版本、磁盘类型与测试时长；**不接受仅凭估算或 Mock 数据判定通过**。

## 8. 性能与可靠性风险

| # | 风险 | 影响 | 缓解 | 残余风险 |
| --- | --- | --- | --- | --- |
| R1 | `stat()` 在杀毒/网络盘上变慢 | 拖慢录制管理线程 | 1 秒低频、单次异常捕获、必要时改为 2 秒采样或分片错峰 | 低 |
| R2 | 写缓存导致速度抖动/为 0 | 用户误判为故障 | 5 秒滑动窗口 + 文案说明 + 停滞阈值 30 秒 | 中（可接受） |
| R3 | 把写入速度误标为码率/下载速度 | 指标失真、误导用户 | 严格按 §3.1 命名；一期不显示码率/下载速度 | 低 |
| R4 | `-progress` 混入 stderr 污染诊断 | 错误排查能力下降 | 字段白名单解析，进度行不进尾部/诊断日志；未知行原样保留 | 中（需测试覆盖） |
| R5 | 新增逐房间信号导致信号风暴 | UI 卡顿 | 不新增逐房间信号，改为 UI 定时拉取 | 低 |
| R6 | 分段切换产生负差分/巨大跳变 | 趋势图与速度异常 | 切换时重置基线与缓冲（§5） | 低 |
| R7 | 重连等待被算入录制时长 | 时长虚高 | 分离"会话时长"与"有效录制时长" | 低 |
| R8 | 指标逻辑与 W-01/W-02 状态机冲突 | 状态显示矛盾 | 指标只读派生，不写库、不发通知、不改变重试 | 低 |
| R9 | `GetProcessIoCounters` 对 socket 不计数 | "下载速度"不可用 | 列为实验项，默不展示；无有效数据时直接省略 | 中（功能可放弃） |
| R10 | UI 每秒刷新影响低配设备 | 界面卡顿 | 仅可见时刷新、单行更新、无动画 | 低 |

## 附录 A：核心公式

```
写入速度(5s)   = [size(t) - size(t-5)] / 5
本场累计大小   = Σ 已完成分段最终大小 + 当前分段大小
分段时长       = now_monotonic - segment_started_at
停滞时长       = now_monotonic - last_growth_at
码率(二期)     = total_size_bytes * 8 / (out_time_us / 1_000_000)
速度比(二期)   = speed 字段（FFmpeg 直接给出）
降速判定       = 近30s均速 < 0.4 × 前60s均速
```
