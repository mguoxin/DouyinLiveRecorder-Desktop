# V0.4.2 稳定性、窗口异常与恢复审计

- 审计日期：2026-11-23
- 基线：`7178d68`（v0.4.1 发布提交），master 与标签同指
- 方法：只读代码审计 + 独立进程受控故障注入 + 现有测试回归
- 环境：Windows 11（10.0.26300），18 逻辑处理器，Python 3.12.16，offscreen Qt；
  未使用真实抖音直播间，未修改生产数据目录

## 1. 结论摘要

1. 录制事件阶段已能区分“分段/会话”，v0.4.1 的 P2-01 修复在代码层成立（RA-01）。
2. 失败通知仍只有状态栏单行文本：启动失败、运行失败、数据库失败共用 `recording_error`，
   缺阶段与可重试语义（RA-02，S2）。
3. 分段失败只发 `recording_finished(status=failed)`，不发 `recording_error`；
   消费端若不看 `status/scope` 会漏报（RA-03，S2）。
4. 续录期间房间行被标记为“录制中”，与“等待重试、无进程”事实不一致（RA-04，S3）。
5. 关闭流程在受控注入下表现正确：确认取消不启动收尾；隐藏状态下先恢复再确认；
   2 秒慢关闭期间窗口可见、内容区禁用、状态明确，2.0 秒完成（RA-05）。
6. 窗口隐藏/恢复 200 次、主题切换 40 次未出现空白或页面丢失（RA-06）。
   **未复现不等于已修复**：异常窗口空白的根因仍未确认。
7. 关闭时禁用整个内容区并使用灰色禁用态，若收尾超过 30 秒，用户可能主观判断为“空白/卡死”（RA-07，S3）。
8. 主题切换每次全量重设 QSS，实测平均约 42 ms；系统主题变化监听会触发同样开销（RA-08，S3）。
9. 长期运行所需的核心保护已具备：轮询异常不终止管理线程、关闭幂等、DB 串行化、
   Job Object 兜底、磁盘与停滞保护（RA-09）。
10. 仍有未实测项：FFmpeg kill 回退、真实弱网、低配真机、多显示器/远程桌面场景（RA-10）。

## 2. 录制事件与状态机

### 2.1 事件现状

| 事件 | 触发点 | 关键载荷 | 消费端 |
| --- | --- | --- | --- |
| `recording_started` | 首次启动 / 续录新分段 | `resumed`、`attempt`、`file_path` | `_on_recording_started` 置录制态，状态栏“开始录制” |
| `recording_reconnecting` | 异常退出、停滞、退出码 0 且无法确认 | `attempt`、`max_attempts`、`delay_s`、`error` | 状态栏“N 秒后自动续录（第 x/5 次）” |
| `recording_finished` | 分段收尾 / 会话结束 | `scope`、`status`、`error`、`file_size` | 置非录制态；会话失败显示“会话结束” |
| `recording_error` | 启动前失败、命令异常、会话级失败、DB 更新失败 | 仅 `room_id, message` | 状态栏“录制错误”，置非录制态 |

代码：`src/dlrecorder/application/recording_service.py:103-107`；
状态机分支：`:521-586`（轮询/磁盘/停滞）、`:608-637`（退出码）、`:662-694`（进入续录）、
`:816-850`（续录失败与预算耗尽）、`:852-876`（无分段会话结束）、`:885-958`（分段收尾）。

### 2.2 阶段区分评估

| 阶段 | 是否有独立语义 | 问题 |
| --- | --- | --- |
| 启动失败（目录不可用、磁盘不足、重复启动） | 否，全部为 `recording_error` 字符串 | 与“录制中途失败”无法区分 |
| 可自动恢复的中断 | 是，`recording_reconnecting` 带次数/延迟 | 文案已表达“自动续录”，但无“已恢复”事件 |
| 重试耗尽/最终失败 | 是，会话级 `recording_finished(status=failed)` + `recording_error` | 两个事件先后到达，状态栏被后者覆盖 |
| 分段失败但会话可能继续 | 部分，`recording_finished(scope=segment,status=failed)` | 不额外发 `recording_error`，易漏报 |
| 恢复成功 | 部分，`recording_started(resumed=True)` | GUI 未区分恢复与首次开始 |

**RA-01（已确认修复）**：`_end_without_segment` 发出 `scope=session` 且 `file_path=""`、`file_size=None`
（`:864-876`），`_close_segment` 发出 `scope=segment` 与真实文件大小（`:946-958`）；
`main_window._on_recording_finished` 已按 `scope` 分支（`:516-544`）。v0.4.0 的 `completed size=0` 误导不再成立。

**RA-02（S2，必须修复）**：`recording_error` 同时承载“不可开始”“运行中失败”“数据库更新失败”，
载荷只有字符串，通知层无法可靠判断“是否会自动恢复”。不得用错误文本正则猜测阶段。

**RA-03（S2，必须修复）**：分段失败只经 `recording_finished` 传达。现有 GUI 只在历史页刷新，
不做用户提示（`:540-543`）。若直接以 `recording_error` 驱动通知，会漏掉分段失败。

**RA-04（S3，建议）**：`_on_recording_reconnecting` 调用 `set_recording(room_id, True)`
（`main_window.py:551-557`），续录等待期间房间行仍显示“录制中”，与“当前无 FFmpeg 进程”不符；
应显示“重连中（第 x/5 次，N 秒后）”。

## 3. 窗口异常与恢复

### 3.1 相关代码路径

- 最小化到托盘：`changeEvent` → `QTimer.singleShot(0, _hide_to_tray)`（`:761-769`）；
  `_hide_to_tray` 再次校验 `_tray is None / _closing / not isMinimized()`（`:259-269`）。
  恢复发生在定时器触发前时，`isMinimized()` 已为 False，不会误隐藏（已排除竞态）。
- 托盘恢复：`show_requested` → `_restore_window`（`:244`、`:271-278`）。
- 关闭：`closeEvent`（`:771-827`）→ 有活动录制且窗口隐藏时先 `_restore_window`（`:791-795`）
  → 确认框 → 收尾线程（`:819-824`）→ 内容区 `setEnabled(False)`（`:815-817`）
  → 完成后恢复启用并 `close()` + `app.quit()`（`:865-878`）。
- 主题：`ThemeManager.apply()` 全量 `setPalette` + `setStyleSheet`，并刷新标题栏（`presentation/theme.py:642-650`）。

### 3.2 受控故障注入（本轮实测）

独立进程、临时数据目录、`QT_QPA_PLATFORM=offscreen`，真实 `MainWindow` + 真实
`MonitorService`/`RecordingService`（Mock 解析器、无房间）；只替换 `ask_confirm` 与
`recording.active_rooms`，并注入 2 秒慢 `recording.shutdown`。结果：

| 场景 | 迭代/条件 | 结果 |
| --- | --- | --- |
| 主题切换 | dark/light 各 20 次 | 1672 ms；4 个页面始终存在；内容区尺寸正常；窗口可见 |
| 隐藏/恢复 | 200 次 | 515 ms；200/200 可见；内容区恢复启用 |
| 关闭确认取消 | 有活动录制，回答“继续录制” | 窗口保持可见；未启动收尾；返回 False |
| 隐藏状态下关闭 | `hide()` 后关闭 | 确认框出现前窗口已恢复可见（100%） |
| 慢关闭注入 | `shutdown` 先 sleep 2 秒 | 关闭期间窗口可见、内容区禁用、状态栏“正在停止录制与监控…”；2.0 秒完成；`_shutdown_ok=True` |
| 托盘不可用 | offscreen 无系统托盘 | `_tray is None`，不隐藏、不崩溃，降级为普通窗口 |

未观察到空白、页面丢失、崩溃、关闭卡死或 `shutdown_finished` 丢失。

### 3.3 未复现问题与根因候选

累计覆盖：隐藏/恢复 200 次、主题切换 40 次、关闭取消/隐藏关闭/慢关闭 3 条路径、
2 个最小化/恢复事件循环调度点。**仍未复现“异常窗口空白”。**

按代码事实列出候选根因（均未证实，不得写入 Release 作为已修复）：

| 候选 | 依据 | 判定 |
| --- | --- | --- |
| B-1 关闭期灰色禁用态被误认为空白 | `central.setEnabled(False)`（`:815-817`） | 可能的主观误判；可通过遮罩/进度替代降低 |
| B-2 全量 QSS 重设造成短暂未重绘 | 每次主题变化 `setStyleSheet`（`theme.py:648`） | 可能；实测单次约 42 ms，未观察到空白 |
| B-3 远程桌面/显卡重置/多显示器 DPI 切换 | 应用外因素；Qt 窗口需重绘 | 未测试（无多显示器/远程环境） |
| B-4 恢复路径缺少显式 `update()` | `_restore_window` 只 showNormal/raise/activate | Qt 通常自动重绘；未证实 |
| B-5 关闭确认框出现在屏幕外 | v0.4.1 已先恢复窗口；注入验证通过 | 已排除 |
| B-6 恢复前最小化定时器误隐藏 | `_hide_to_tray` 复查 `isMinimized` | 已排除 |

**RA-06（S2，需进一步实测）**：窗口空白未复现。需要现场复现包（故障时刻的日志、
显示器拓扑、DPI、远程会话状态）才能定位；v0.4.2 先增加“异常窗口现场记录”能力
（见诊断导出），不得宣称已修复。

**RA-07（S3，建议）**：关闭期间禁用内容区，低配设备或慢磁盘上若收尾接近 30 秒，
灰色空内容 + 不响应鼠标会被误判为卡死。建议改为覆盖式进度层（保持内容可见）或
至少显示进度文案而不禁用整个 central widget。

**RA-08（S3，建议）**：`ThemeManager.apply()` 每次都重建 palette/stylesheet；
系统主题变化（`colorSchemeChanged`）也会触发。实测 42 ms/次可接受，但在远程桌面下可能放大。
建议仅在有效主题变化时重设 QSS（当前 `_on_system_scheme_changed` 已按 before/after 判断，
但 `apply()` 内部仍无条件重设）。

## 4. 长期运行与故障恢复（静态审计）

| 关注点 | 代码事实 | 结论 |
| --- | --- | --- |
| 轮询异常 | `_run` 捕获 `Exception` 并继续（`recording_service.py:356-384`） | 单次轮询异常不会杀死管理线程 |
| 关闭幂等 | `_shutdown_report` 缓存 + 锁（`:321-353`） | 重复关闭安全；超时有 critical 日志与剩余活动数 |
| 数据库并发 | `RLock` + 单连接 + `check_same_thread=False`（`db.py:47-64`） | 读写串行化；长查询会阻塞 GUI 读取 |
| 数据库/文件一致性 | 先写 `recording` 记录再启动进程；收尾 `finish_recording` 幂等（`:789-808`）；启动恢复把遗留记录标记 `interrupted` | 崩溃后可按文件大小回填 |
| 进程清理 | Job Object + 进程登记表 `(PID, 创建时间, 路径)` 身份核验 | 仅身份完全匹配才终止，避免误杀 |
| 磁盘保护 | 开始前阻止；轮询中低于阈值停止并 `_finalize`（`:530-550`） | 不自动删文件 |
| 输出停滞 | 120 秒无增长 → 停止；预算允许则续录（`:555-586`） | 网络中断可自愈，预算耗尽才失败 |
| 日志内存 | `LogWidget._messages` 为有界 `deque(maxlen≈500)`（`widgets.py:450`） | GUI 日志不会无限增长 |
| 文件日志 | 5 MB × 3 轮转（`logging_config.py:22-24`） | 长期运行磁盘占用有界 |
| FFmpeg 诊断日志 | 256 KiB 单文件轮转（`ffmpeg.py:58-127`） | 有界 |
| 关闭耗时 | 录制服务 join 30 秒上限（`:321-353`）；GUI 后台线程无硬杀 | 极端情况只提示不中断 |

**RA-09（已具备，无需改动）**：上述保护覆盖了崩溃、断网、磁盘不足、进程残留与日志膨胀的主要路径。

**RA-10（需进一步实测）**：以下只有静态证据，缺少运行时测量：
FFmpeg kill 回退（q → terminate → kill 的第三段，`ffmpeg.py:462-484`）、
真实弱网下的续录、低配真机资源曲线、多显示器/远程桌面下的重绘、长时间句柄增长。
性能结论必须由 v0.4.2 的专项测试产出，本轮不给出新的性能结论。
