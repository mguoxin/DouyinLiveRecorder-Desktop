## 1. 失败证据

2026-11-27 首次全量回归（同时存在另一个 pytest 进程）：

```
FAILED tests/test_recording_service.py::test_unknown_status_retry_is_bounded
assert len(started) == 1
E   assert 0 == 1
322 passed, 1 failed in 202.19s
```

隔离运行同一用例 3/3 通过，说明失败与调度竞争相关，而非稳定功能错误。

## 2. 根因

原测试：

```python
service.start_recording(env.room_id, "...")
_wait_for(qt_app, lambda: not service.is_recording(env.room_id), timeout=20)
time.sleep(0.3)
qt_app.processEvents()
assert len(started) == 1
```

`start_recording` 只是把命令放入队列。命令尚未被管理线程处理时，
`is_recording()` 仍然为 `False`，等待条件立即成立；随后固定 `sleep(0.3)`。
在 CPU 竞争下，管理线程可能超过 0.3s 才处理命令，导致 `started` 仍为空。
这是**测试同步条件错误**，不是 `RecordingService` 的状态机缺陷。

## 3. 修复

```python
service.start_recording(env.room_id, "...")
# 先等本轮结束事件，确保 start 命令已被管理线程处理；
# 仅等 is_recording 为 False 会在命令入队前就成立，导致断言竞态。
_wait_for(qt_app, lambda: bool(finished), timeout=20)
_wait_for(qt_app, lambda: not service.is_recording(env.room_id), timeout=20)
qt_app.processEvents()
```

- 等待 `recording_finished` 事件（该事件只会在 start 已被处理、会话结束后发出）。
- 再等待活动任务移除，保证后续数据库断言稳定。
- 删除固定 `time.sleep(0.3)`，不改变任何断言与超时余量。

同时审计了同文件中另外两处 `not is_recording` 等待：

| 位置 | 是否安全 | 原因 |
| --- | --- | --- |
| 停止录制用例（约 L344） | 安全 | 之前已等待 `started` |
| 停滞续录用例（约 L545） | 安全 | 之前已等待 `started == 2` |
| 本用例（原 L512） | 不安全 | 无任何前置事件等待 |

## 5. 残余风险

- 测试仍依赖真实计时（`poll_interval_s=0.03`）验证有界重试；极端系统暂停仍可能超时，
  但不会再出现 `started==0` 的误判。
- 其他历史用例中的固定 `sleep` 未全面清理；本轮只处理已确认失败路径，避免大范围改动。
