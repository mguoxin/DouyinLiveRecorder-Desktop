## 2. 代码审查与风险清单

审查链路：解析（parser）→ 监控（task_manager / monitor_service）→ 自动录制（app）→ 录制状态机（recording_service）→ FFmpeg 进程（ffmpeg）→ DB → 退出清理。

| 编号 | 严重度 | 问题 | 状态 |
| --- | --- | --- | --- |
| R1 | 高 | 自动录制开启时，用户手动停止后，下一次 `room_state_updated`（仍 LIVE）会重新启动录制 | **已修复**（app.py 手动停止抑制集合 + 2 个回归测试 + 真实环境验证 A4） |
| R2 | 中 | 真实下播时 FFmpeg 退出码与状态时序未知，可能走满退避后标 failed 而非 completed | 尚未验证（见 §7） |
| R3 | 中 | stop 后无法确认进程退出（`report.exited=False`）时标 failed 并提示"可能仍在写入" | 存在已知风险（未触发，行为偏保守） |
| R4 | 低 | 续录等待期确认下播结束时，`recording_finished` 携带 `file_size=0`（UI 显示 0 字节） | 存在已知风险（不改数据） |
| R5 | 低 | 管理线程未在超时内退出时，仍继续关闭监控服务 | 存在已知风险（极端低概率） |
| R6 | 中 | FFmpeg 启动成功但无数据 → stall_timeout(120s) 主动停止且不触发续录 | 设计限制（自动录制模式下由下一次监控轮询恢复） |
| R7 | 低 | `completed` 仅代表退出码 0 且文件非空，不做可解码校验 | 存在已知风险（本轮外部解码抽样全部通过） |
| R8 | 低 | `current_session_id` 无锁读，极限时序下新录制可能关联已结束 Session | 存在已知风险（仅影响追溯） |
| R9 | 低 | `remove_room` 先删房间再发 `room_removed` | 已通过（记录 room_id 置 NULL，按 id 更新正常） |
| R10 | 中 | 多房间隔离依赖单管理线程 + 每房间独立进程/文件 | 已通过（B2 强杀验证） |
| R11 | 中 | 断网/地址过期依赖 FFmpeg reconnect + 退出后续录 | 部分通过（见 §6） |
| R12 | 低 | 文件命名冲突/覆盖 | 已通过（命名含秒级时间 + 6 位 uuid；B3 路径唯一） |
| R13 | 低 | 启动恢复遗留会话/记录 | 已通过（C9：recording→interrupted，running→interrupted） |

### 本轮新发现

| 编号 | 严重度 | 问题 | 状态 |
| --- | --- | --- | --- |
| N1 | 高 | FFmpeg 因网络 EOF 以**退出码 0**结束，原逻辑直接标记 completed，导致"直播间仍在播却停止录制" | **已修复**：退出码 0 时重新解析，确认仍在直播则新文件续录；确认下播/无法确认才收尾。单元测试 2 项 + 代理故障注入验证 |
| N2 | 中 | 软件异常退出后，FFmpeg 子进程成为孤儿并继续写入文件 | 存在已知风险（无持久化 PID，修复需引入进程跟踪或改 Schema；本阶段不做） |
| N3 | 低 | 续录次数为整场累计，成功后不重置；长时段多次小中断会提前耗尽重试 | 存在已知风险（当前上限 5 次，退避 2/5/10/20/30s） |
| N4 | 低 | 连接未建立即失败的记录为 failed、0 字节且磁盘无文件 | 行为可解释（FFmpeg 未创建输出）；UI 会显示一条 0 字节历史 |
| N5 | 环境 | 测试中期抖音解析接口开始返回验证码页（`API_MALFORMED`），真实解析链路不可用 | 记录为环境限制；后续用缓存真实流地址完成网络/并发测试 |

未发现静态缺陷的部分：FFmpeg 参数顺序与输入/输出分组、stdin `q` 收尾、退出码判定、DB 幂等更新、多线程 DB 锁、关闭顺序（录制先于 DB）、`build_record_command` 的 HTTP(S) 重连参数范围。

## 5. 异常与故障注入（C）

### C1 FFmpeg 被强制终止

- 第二阶段证据：强杀后 60.6s → 65.5s 完成续录（2 个分段，`thread_exited=true`）。
- 本轮 B2 复验：强杀单房间后 2.0s 续录，仅该房间受影响。**已通过**。

### C2 网络短暂中断（8s，模拟）

方法：本地 TCP 代理转发真实 CDN 流，20s 时断开全部连接并拒绝新连接 8s（**模拟故障注入**）。

| 结果 | 数据 |
| --- | --- |
| FFmpeg 表现 | 连接 EOF 后以**退出码 0** 退出（旧逻辑会误判为正常结束） |
| 修复后行为 | 重新解析确认直播中 → 分配新文件续录 |
| 分段 | 21.78s（17.6 MB）+ 31.82s（24.0 MB），中间 1 条 0 字节失败尝试记录 |
| 段间缺口 | 约 7s（按文件时间与 TS 时长估算） |
| 分段质量 | 两段均全解码通过，CC 断点 0，PCR 跳变 0 |

结论：**已通过（修复 N1 后）**。修复前该场景会导致录制提前结束（长测中已实测复现，见 §8）。

## 12. 已知风险汇总

1. **孤儿 FFmpeg（N2，中）**：软件异常退出后子进程继续写文件，重启前文件持续增长，DB 大小快照偏小。建议后续引入"启动时按录制目录与自身命令特征清理孤儿进程"或持久化 PID（涉及 Schema，需单独审批）。
2. **重试次数累计不重置（N3，低）**：长时段多次中断可能提前耗尽重试次数。建议后续评估"成功续录后重置计数"或按时间窗口限流。
3. **0 字节失败记录（N4，低）**：连接未建立即失败时产生无文件的历史记录。
4. **completed 不做解码校验（R7，低）**：本轮 10 个产物全部解码通过，但代码层不校验。
5. **速率限制（环境）**：高频解析会触发抖音验证码页，导致自动续录/监控解析失败；程序行为为有界重试后失败，不会死循环。

## 15. 验收核实：`recording.auto_start` 语义与行为一致性（v0.1.2 冻结前）

核实背景：报告称该配置"默认关闭"，而真实环境实测"手动启动监控后 1 秒内自动触发录制"，需确认配置项与实际行为是否矛盾。

### 1. 定义、读取位置与控制范围（代码事实）

- **定义**：常量 `AUTO_RECORD_SETTING = "recording.auto_start"`，仅存在于 `src/dlrecorder/application/app.py`（L32），全项目无其他模块读写该键。
- **读取**：应用启动时一次（L115 `self._auto_record = self.db.get_setting(AUTO_RECORD_SETTING, "0") == "1"`），**键不存在时默认 `"0"`（关闭）**；此后以内存值为准，UI 勾选框按该值回显（main_window.py L106）。
- **写入**：工具栏"自动录制"勾选框切换 → `_set_auto_record()`（L223-230）持久化到 settings 表。
- **控制范围**：仅 `_on_room_state_updated()` 第一行 `if not self._auto_record: return`（L164）——即"监控确认开播后是否自动开始录制"。**不影响**手动"开始录制"按钮，也不影响录制状态机、续录与停止逻辑。

### 2. 默认关闭时是否应自动开始录制？

**不应。** 关闭时监控仍正常轮询并更新房间状态，但不自动启动录制。这与代码（L164）一致，也与旧版故障现象一致（用户 v0.1.1 数据库无该键 → 监控 running 但 recordings 表为空）。

### 3. 15:27"1 秒自动触发"是否矛盾？

**不矛盾。** 该实测的前提是数据迁移脚本按已批准的迁移方案显式写入 `recording.auto_start=1`（即"开启自动录制"）。证据：

- 0.1.2 打包版数据库 settings 表（只读查询）：`recording.auto_start = 1`。
- 打包版 `app.log` 三次启动（15:22:26 / 15:25:18 / 15:26:03）均打印"自动录制已启用"，证明启动时读取到开启值并生效。
- 行为符合设计：15:27:00 开始监控 → 首轮轮询确认开播 → 15:27:01 自动开始录制。

### 4. 命名与报告表述

- 命名 `recording.auto_start`（recording 命名空间，含义"确认开播后自动开始录制"）与 UI 文案"自动录制"一致、准确。
- 报告原表述"默认关闭"（指用户旧库）与"1 秒自动触发"（指迁移开启后的新库）各自准确，但未点明因果，已在 §13/§14 补充说明。

### 核实结论

**未发现配置项与实际行为不一致，无代码缺陷；仅报告表述补充说明，业务逻辑零改动，v0.1.2 冻结不受影响。**
